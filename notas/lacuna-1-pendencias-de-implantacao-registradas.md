### F. What the app does when a piece is missing (the basis of the inferences)

After a failed opening the days are already stored at the new format, so an old tab's next save of one of them is refused too (inferred from the guard: 20261110213600:71-74; README.md:164-167).

## Implications for the plan (suggestions)

Each one is a suggestion, with its cost and its risk.

1. **Step 0, before the plan fixes any order: a read-only inventory of both projects, by Pedro.** `supabase migration list` and `supabase db push --dry-run` per project (CLI); `supabase functions list` and `supabase secrets list` (names only, CLI); and read-only SQL in the style the repo already uses (`supabase db query --remote=<ref> -o json --read-only`, scripts/semear-dias-previa.mjs:27): the cadastro's `conteudo->>'esquema'` and `versao`; `conteudo->>'esquema', count(*)` over `public.dias`; `proname, pronargs` from `pg_proc` for `registrar_solicitacao`, `salvar_dados_pessoais`, `importar_cursos`, `painel_do_dia`; `count(*)` of `public.perfis` where `perfil = 'secretaria'`. Cost: minutes. Risk: none while read-only; type the production ref with care, since only the two seeding scripts refuse it (scripts/semear-previa.mjs:12-17). Note for whoever reads the answer: "conversion done" is the cadastro at `esquema` 24 or more; an empty `versoes_dos_cursos` does not disprove it, because `importar_cursos` skips a program equal to the stored one (20261117200000:610) and the program "starts empty until ACPM enters the official program" (docs/PLAN.md:247).
2. **A catch-up step with no feature in it, before the first new migration.** Preview: bring the fork's published branch to upstream/main, push what step 0 shows as pending (expected #26, possibly #25 and #24), set the secret and deploy the function, run `npm run test:db` from an unchanged upstream/main, fix test/e2e/publicado.spec.js:62 and run it. Then production. Then one docs commit that ticks or rewrites docs/PLAN.md:159-160 and 408-411 and replaces "Not deployed" and "Not applied" with dates. Cost: an hour if all is green; up to a day if Postgres 17 or real pgTAP disagrees with the stand-in. Risk: a failing check in an applied migration needs a corrective migration, which must then come before the plan's two; better found here than inside workstream A or D.
3. **Give the plan's migrations one lineage and explicit names after `20261120150000`.** `db push` takes whatever the worktree holds. A push from a worktree that lacks a version already on the remote is refused, and one that holds an older unapplied file needs `--include-all` (CLI). So A and D cannot each push from their own worktree: put the migration files in the serial foundation, or stack D's branch on A's, and let one branch do every push. Cost: A and D lose their independence on the server side. Risk of not doing it: a blocked push on the shared preview, and each branch's copy of the pgTAP files pinning a schema the preview no longer has (mapa-banco 5.7, last paragraph). There is no semantic dependency on the pending files: #25 touches the course tables and `registrar_resultado`, #26 only `painel_do_dia`, A only `salvar_dados_pessoais`, D only `solicitacoes` and its functions.
4. **Take the two legacy overloads along, as the first migration, on its own.** One file with two `drop function` statements, applied to the preview, tested, applied to production, all before any feature migration. It is safe "before the merge" because the app on main calls neither (js/backends/supabase.js:219-222, 258-260). Cost: `agenda.test.sql` moved to the 10-argument signature (nine call sites: :35, :41, :43, :45, :51 and :62 need a specific time and a duration to reach the rule they test, because the new function checks those first, 20261114230012:22-29; :47 and :49 change from 23514 to 22023; :69 only gets the extra arguments), `contas.test.sql:27`, two `has_function` turned into `hasnt_function` (agenda-horas.test.sql:18-19, dados-pessoais.test.sql:42-43), the e2e fake refusing a call without `p_horas` (test/e2e/supabase-falso.js:377-386) and test/unit/backend-supabase.test.js:479, 481. Risk: a tab open since before 2026-11-14 gets a generic error on registering a pedido or saving personal data. Gain: A then changes one function with one signature, D's rules cannot be bypassed, and the 10-argument function gets the role and exception tests it lacks today (mapa-banco, note under section 6).
5. **Alternative to 4: fold each drop into its workstream** (A drops the 3-argument one, D the 9-argument one). Cost: fewer files. Risk: a removal inside a feature migration, against the expand-only habit (mapa-banco 5.5), and the agenda bypass stays open until D lands.
6. **Leave `importar_cursos` out of both, as its own last step (step I, or after the redesign).** Its precondition is per server and probably false on the preview (section G); it has a client side (js/storage.js:339-341, 374, 394; js/backends/supabase.js:305-309; the `'cursos-pendentes'` notice, js/storage.js:31, 211, 320-325 and js/views/cursos.js:31) and about eight test files (section D). Risk of doing it early: an app without the call opening a cadastro below 24 marks the conversion done without bringing the programs, and a re-seeded preview is below 24 (scripts/semear-previa.mjs:23-28). Risk of never doing it: none on a converted server, where the function returns 0.

Cost: small. Risk: none; it is what docs/PLAN.md:119-122 and 135-138 did while they were kept.
8. **Write each go-live list so the first two lines are checks, not actions:** the output of `supabase migration list` for the target, and `supabase db push --dry-run` showing exactly the files the step means to apply. Cost: two commands per push. Risk: none. It is the direct guard against "`db push` applies every pending file".
